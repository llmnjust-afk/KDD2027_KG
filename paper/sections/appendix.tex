\section{Experimental Details}
\label{app:setup}

\paragraph{Hardware and software.}
All experiments run on a single workstation: NVIDIA RTX~5090 (32\,GB VRAM), 124 CPU cores, 925\,GB RAM, Python~3.10, PyTorch~2.11 (CUDA~12.8), transformers~5.14, sentence-transformers, networkx~3.4. No distributed training or multi-GPU inference is used. The 7B model consumes ${\sim}15.4$\,GB VRAM in bfloat16; the 1.5B model consumes ${\sim}3.6$\,GB.

\paragraph{Models, decoding, and cost accounting.}
The generator/judge is Qwen2.5-\{1.5B,7B\}-Instruct. Entity linking and the vector-RAG baseline use \texttt{sentence-transformers/all-MiniLM-L6-v2} for embeddings. Decoding is greedy (temperature $0$, \texttt{do\_sample}=false) with \texttt{max\_new\_tokens}${=}64$ for the judge and $32$ for answer generation, making a single seed deterministic for a fixed input; the multi-seed study (\Cref{tab:sig-seeds}) varies the random seed that shuffles the test-split order before sub-sampling, so different seeds evaluate different query subsets. The per-hop candidate cap is $c_{\max}{=}16$ (i.e.\ each judge call scores at most $16$ triples), which bounds judge prompt length and hence per-hop token cost. We report input tokens to judge and generator as the primary cost metric; output tokens are small (judge outputs $\le$ a few dozen integers, answers $\le 32$ tokens) and end-to-end latency tracks judge-call count on our single-GPU setup.

\paragraph{Prompts.}
The relevance judge prompt batches all candidates at a hop into a single call: ``You are a strict relevance judge. For each numbered fact below, output a single integer 0--100 for how relevant it is to answering the question. Output ONLY a comma-separated list of integers, one per fact, in order. Question: \{q\} Facts: \{candidates\} Scores:''. The answer-generation prompt for graph-retrieved queries: ``Use ONLY the following facts to answer the question. Answer with a short phrase or a pipe-separated list of entities. If the facts are insufficient, answer 'unknown'. Facts: \{subgraph\} Question: \{q\} Answer:''. For graph-free queries (D1 skip): ``Answer the question briefly. Give a short phrase or a pipe-separated list. Question: \{q\} Answer:''.

\paragraph{Entity linking.}
Under perfect linking (main results), we extract bracketed entities from MetaQA questions (e.g., ``[Michelle Trachtenberg]'') and match them exactly against KG entities. Under noisy linking (\Cref{sec:exp-2a}), brackets are stripped and linking falls back to cosine similarity between the question embedding and all KG entity embeddings (43{,}234 entities, embedded once and cached). Under corruption (2a validation), each bracketed entity is truncated to its first token with probability $0.5$ before exact matching, simulating partial-name recognition.

\paragraph{Hyperparameters.}
\Cref{tab:hyper} lists all controller hyperparameters. None are learned; all are fixed across all experiments (1.5B, 7B, all hops) except $\theta_{\text{low}}$ which is raised to $0.75$ only in the corruption study to activate (D1).

\section{Derivation of the Call-Count Accounting (Remark~\ref{prop:cost})}
\label{app:proof}

Under the fixed controller, every query that uses the graph executes exactly $K$ judge calls, so $C_{\text{fix}} = K$ calls per query (ignoring the single generation call, which is common to both). Under \method{}, a fraction $\rho_u$ of queries are routed to the graph-free path by (D1), incurring $0$ judge calls. The remaining $1-\rho_u$ fraction enters the retrieval loop, where (D3) terminates at hop $k^*(q) \le K$. The mean number of judge calls for these queries is $\mathbb{E}[k^*(q)] = \bar{k}_{\text{stop}} \le K$. Therefore $C_{\text{ada}} = (1-\rho_u)\,\bar{k}_{\text{stop}} \le (1-\rho_u)\,K = (1-\rho_u)\,C_{\text{fix}}$. The inequality holds because (D3) can only stop at $k \le K$, never later. This is a direct counting argument, not a theorem: it bounds \emph{call count}, and token cost tracks it only up to per-hop candidate-count variation (candidates are capped at $c_{\max}$, so the token-cost ratio is within a bounded factor of the call-count ratio). It says nothing about accuracy, which we characterize empirically in \Cref{sec:exp,sec:exp-boundary}.

\section{Adaptive Beam Sweep on the Mixed Stream}

\section{Counterfactual Stop-Safety: Force-Continue Analysis}
\label{sec:exp-counterfactual}

A reviewer rightly notes that comparing $P(\text{correct}\mid\text{stopped})$ vs $P(\text{correct}\mid\text{continued})$ suffers selection bias (stopped and continued queries differ in difficulty). The correct test is counterfactual: take the queries (D3) decided to stop, \emph{force} them to continue to max-hops (disabling D3, keeping D1/D2 identical), and measure whether the answer improves. We run this on 7B/2-hop ($n{=}200$). \method{} stops early on $128/200$ queries ($64\%$). On these, force-continue \emph{strictly improves} F1 on only $10$ ($7.8\%$ false-stop rate), \emph{hurts} on $24$ ($18.8\%$), and leaves $94$ unchanged; the mean answer change is $-0.032$ (force-continue lowers F1). Overall, stopping saves $0.65$ hops/query while \emph{raising} F1 by $+2.1$ ($0.402$ vs $0.382$). The stopping signal's AUROC for predicting ``force-continue helps'' is $0.503$ on all queries---near chance, consistent with the low false-stop rate. This validates (D3) is safe on 7B/2-hop: the pruned hops carry noise, not evidence, even though the same judge is noisy enough at depth 3 that global $K{=}2$ beats per-query adaptation on the mixed stream (\Cref{sec:exp-mixed}). The boundary is about \emph{where} the judge is noisy (depth 3 on 3-hop queries), not whether stopping is safe in general.

\section{Strong-Engine Transfer (14B)}
\label{app:strong-engine}

To test whether \method{}'s benefit transfers to a stronger GraphRAG engine, we swap the 7B generator/judge for Qwen2.5-14B-Instruct (Qwen3-8B was unavailable in our environment) and re-run 2-hop retrieval ($n{=}150$, same KG and questions as the 7B main result). \Cref{tab:strong-engine} reports the full comparison. \method{} improves F1 by $4.7\%$ ($0.506\to0.530$) while reducing cost by $15\%$ ($1487\to1266$ \Toks{})---a simultaneous F1 and cost win that does \emph{not} hold under the 7B judge on the mixed stream (\Cref{sec:exp-mixed}). This is the cleanest evidence for the judge-quality scope condition: the same controller, on the same KG, succeeds when the judge is reliable and fails when it is noisy at depth.
